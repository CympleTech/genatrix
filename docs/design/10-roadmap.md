# Genatrix · 路线图

> 状态：v0.4 · 已通过（2026-09-14）
> v0.4 变更：新增"底座与 agent 框架"一段，位于第一次外部用户之后、第二阶段之前。
> v0.3 变更：去掉全部日期与外部计划的引用，只按阶段与里程碑排序。
> v0.2 变更：技术验证加阈值与失败决策，新增沙箱验证；M2 里 Telegram 不阻塞主线；外部用户的知情同意。
> 回答的问题：先做什么、后做什么、每一步做到什么算完成、什么会让它失败。

## 一条约束

**来自 00 号。** 第一阶段近乎固执地只证明一个闭环：可信地收集 → 本地理解 → 产生有用的摘要 → 经批准完成一次行动。任何不在这四个环节里的东西，不进第一阶段。

路线图不写日期。一个人做，节奏由你控制。里程碑不缩水，只推后。

## 总览


## 技术验证

四个，每个限一天，只回答一个问题，不产出可保留的代码。通过阈值和不通过时的决策写在前面，避免做完再找理由：

| 验证 | 回答的问题 | 通过阈值 | 不通过则 |
|---|---|---|---|
| 沙箱 | macOS 沙箱能否阻断一个进程的全部出站网络，同时保留 unix socket 监听与内存映射加载几 GB 权重 | 三项同时成立，推理速度无明显下降 | 04 号两进程方案改为网络扩展，或撤回"操作系统保证"的表述，如实改为代码保证 |
| 本机模型 | 在这台 16 GB 的 Mac mini 上，一个 8B 4 bit 模型做判级和摘要，速度和质量能不能接受 | 判级每条 500 ms 内，50 条人工抽样同意率 85% 以上；摘要每条 5 s 内，读着有用 | 判级退为纯规则加更小的模型；摘要接受更差的质量或缩小 M2 的摘要目标 |
| Telegram 登录 | Rust 的 MTProto 库能否完成手机号登录、两步验证、拉对话列表、翻一个大群的历史 | 四步全部完成，翻 1 万条消息不触发限制 | 换库；都不行则 Telegram 推到第二阶段 |
| Gmail IMAP | 应用密码登录、Gmail 扩展可用性、回填速度 | 扩展可用；回填 1 万封含正文的邮件在 30 分钟内 | 扩展不可用则退到标准 IMAP 重建线程；速度不够则回填改为先头后体 |

验证结果记录在 `docs/plan/spikes/`。

## 第一阶段 · 助理

四个里程碑，每个对应闭环的一个环节。每个里程碑结束时你自己在用它。

### M1 · 收集

- IMAP 连接器：接入、回填、实时同步、恢复。
- 时间线界面加搜索，只有全文，没有向量。
- 菜单栏图标与状态。

**完成的定义**：你的全部 Gmail 历史在本机，可搜，新邮件几秒内出现。连续七天没有漏、没有重、没有需要手动干预的中断。

### M2 · 理解

- 出境闸门、账本、规则文件。此时没有云端，闸门只放行本机，但账本已经在记。
- classifier、embedder、summarizer 三个角色，本机。
- 入库流水线完整：判级、分块、向量、摘要。
- 记录页。
- Telegram 连接器，作为不阻塞项：M2 完成不以它为条件，它最迟在 M3 结束前落地。"理解"主线不被第二个数据源的意外拖住。

**完成的定义**：每条 Item 有级别和摘要；向量搜索可用；记录页显示"0 字节离开过这台设备"。你抽查一百条判级，同意率高于 90%。

### M3 · 摘要

- 每日摘要流水线；承诺提取流水线。
- "今天"页。
- Person 页与关系统计。

**完成的定义**：连续十四天，每天早上有一份摘要；你认为其中至少一半的条目是有用的；"你答应过的"分组至少抓到过一件你确实忘了的事；邮件和 Telegram 已混排在同一条时间线上。

### M4 · 行动

- Action、审批面板。
- drafter 角色；改稿与拒绝理由的记录。
- IMAP 发送、Telegram 发送、回流。
- 对话页。

**完成的定义**：00 号的成功标准全部达成。你连续三十天在用；至少一次它起草的回复经你批准发出，记录里能回放整个过程。

第一阶段结束时云端仍然是关闭的。云端在第二阶段打开，理由是先证明纯本机成立。

## 第一次外部用户

一个人。你的朋友，不是开发者。目标是 09 号的判据：这位朋友自己装、自己接账号、第二天收到摘要。你不能在旁边帮。开始之前要讲清楚三件事并得到同意：全部邮件和消息会下载到那台电脑上；Telegram 登录会在手机上显示新设备；随时可以一键删干净。

这一段的产出不是功能，是安装与恢复流程的修正清单。

## 底座与 agent 框架

11 号的功能型 agent。放在外部用户之后，是因为底座本身先要被一个非开发者证明能用；放在第二阶段之前，是因为自动批准规则会作用于 agent 提的动作，框架要先定型。

- WASM 运行环境、清单、窄口子的 WIT 接口、固定模板的卡片。
- 安装、升级、回滚、重放比较。
- 附件文字提取（PDF），给 blobs.text。
- 第一个 agent：NZ 报税，来自 finance 项目。
- 第二个 agent：一个和报税完全不同的场景，检验接口是否通用。
- 开发指南与本地测试工具，然后才对外开放。

**完成的定义**：两个 agent 都只用公开的口子写成，没有为任何一个开后门；报税 agent 用你一个 GST 周期的真实发票跑通，每一笔账经你批准；02 号第 13 到 19 条不变量各有测试。

## 第二阶段 · 代理

- 云端开关与脱敏。三档质量测量：本机、脱敏云端、不脱敏云端，用你自己的评测集。**测量结果写成文章。**这个数字目前没有人为个人场景发表过。
- 低风险动作的规则自动批准。
- 画像的 Fact 与冲突裁决。
- 日历连接器。
- 语音消息本机转写。

## 第三阶段 · 分身

到时候设计。前提是画像和审计记录积累到足够的量，且第二阶段的自动批准没有出过让你后悔的事。

## 写作

每个里程碑一篇文章，中文先写。这是你说的"到时候写文章推广"的素材，也是逼自己把每一步讲清楚的方式。

| 时点 | 文章 |
|---|---|
| 设计定稿 | 为什么个人 AI 的第一性问题是数据归属，不是模型 |
| M2 | 三级敏感度和一道闸门：一个普通人能理解的隐私模型 |
| M4 | 一个月，我让一个 AI 读了我全部的邮件和消息，它替我发了三封 |
| 外部用户之后 | 让不会用终端的人跑起本机 AI，我们改了哪些东西 |
| 第二阶段 | 隐私的价钱：脱敏让 AI 的帮助下降了多少 |

## 风险

按发生概率排。

| 风险 | 后果 | 缓解 |
|---|---|---|
| 8B 模型在 16 GB 上质量不够 | 摘要没用，闭环的"理解"环节不成立 | 技术验证先测；规则先行减少模型负担；接受第一版质量一般 |
| 你的时间被其他工作占满 | 全部后移 | 不写日期；里程碑不缩水，只推后 |
| Google 进一步限制应用密码 | Gmail 接不进来 | 观察；如果发生，被迫做 OAuth，但只给 Gmail |
| Telegram 对共享应用凭据的账号限流或封禁 | Telegram 接入不稳定 | 连接器极度保守；申请正式的应用凭据 |
| Rust 前端生态拖慢界面迭代 | M1 到 M4 每个都晚 | 06 号预留了换 TypeScript 的退路，M1 结束时评估 |
| crabllm 上游变化或停更 | 网关维护成本上升 | vendor 进来，我们自己维护，不追上游 |
| 范围失控 | 第一阶段做不完 | 00 号那四个环节；任何新需求先问是不是四环节之一 |

## 每个阶段结束时问的三个问题

1. 00 号的五条原则，有没有哪一条在实现中被妥协了？
2. 你自己还在每天用吗？
3. 下一阶段要做的事，是不是当前阶段的用户真的需要的？

三个问题任何一个答案不好，停下来，回到设计。

## 已裁决（2026-09-14，全部按建议通过）

1. 四个各一天的技术验证，带阈值，在第零阶段之前做完。
2. 不写日期，节奏由你控制。
3. 第一阶段结束时云端仍然关闭。
4. 第一个外部用户是一个非开发者朋友，人选你定。
5. 每个里程碑一篇文章。
