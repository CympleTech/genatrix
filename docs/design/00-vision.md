# Genatrix · 愿景与原则

> 状态：草稿 v0.3 · 2026-09-25 · 已通过（2026-09-14）
> v0.3 变更：定位为服务个人的数据与安全底座；具体业务由功能型 agent 承担（11 号）。
> v0.2 变更：一句话分内外两版；第一阶段闭环写死；易用性升为核心产品；补"为什么长期成立"。

## 一句话

对外：

> 一个只在你设备上运行、理解你的数字生活、并在你批准下行动的 AI。

对内的北极星：

> 掌管你的全部数字生活，只对你负责。

两句是同一件事。对外用"理解、协助、经批准行动"建立信任，对内用"掌管"提醒自己终局有多大。任何一处对外文案出现"掌管"，都算写错。

对企业是不出内网，对个人是不出设备。Genatrix 是后半句。

## 为谁做

普通人。不是开发者，不是极客。

判据只有一条：一个不会用终端的人，能不能在自己的电脑上把它装起来、把邮箱和聊天接进去、第二天早上收到第一份摘要。做不到，就是没做完。

这条判据决定了很多技术选择：邮箱走 IMAP 加应用密码而不是 OAuth 开发者凭据，Telegram 走手机号登录而不是 Bot Token，模型下载是一键而不是一段命令。

它也决定了什么算"核心产品"。安装、模型下载、账户授权、断线恢复、备份迁移，这五件事在普通人眼里就是产品本身。它们和数据模型、agent 层享有同等的设计优先级，有自己的设计文档，不是接入细节。

## 它是什么

- 你所有数字化痕迹的唯一归属地。邮件、消息、日程、笔记、文件，都归一到一个模型里，存在你的设备上，用你的密钥加密。
- 一个读过这一切的 AI。它替你整理、检索、提醒、起草，逐渐知道你是谁、在乎什么、和谁有什么关系。
- 未来分身的种子。当它足够了解你，它可以在你授权的边界内，以你的身份对外行动。

## 底座与功能

Genatrix 永远是服务个人的数据和安全底座。内置的只有三类：连通数据源；理解与整理数据；一套安全的运行方式，管住其他功能。

报税、记账、行程这类具体业务不进底座。它们是功能型 agent，由你自己（用你自己的大模型）或别人来写，装进来，在沙箱里读它声明过的数据，提需要你批准的动作，别的什么都碰不到。我们写的 agent 也一样，没有特权。见 11 号。

## 它不是什么

- 不是又一个聊天框。对话只是入口之一，时间线和审批面板同样重要。
- 不是云服务。没有账号系统，没有服务器端，没有遥测。
- 不是企业产品。单用户，单设备起步。
- 不是密码学项目。加密只在需要的地方出现，不做证明系统，不上链。

## 五条原则

每一条都是硬约束，设计冲突时按顺序取舍。

1. **数据不出设备。** 原始数据只存在本机。云端模型只能看到经过脱敏、且被明确放行的内容。默认拒绝出网，放行需要理由并留痕。
2. **权限不越界。** 参数就是能力。一个连接器能碰哪个账号、一个工具能读哪个范围，写在声明里；没声明的，代码里不存在到达它的路径。
3. **每一步可追溯。** AI 做过的每一件事：读了什么、依据什么、输出什么、谁批准的，都是一条可回放的记录。你能审计自己的 AI，别人不能。
4. **模型可替换，agent 层零依赖。** 模型是可插拔的推理资源，今天是云端大模型，明天是本机 8B。规划、工具分派、记忆、权限、审批全部在我们自己的 agent 层，不依赖任何厂商的 API 特性。小模型加好的 agent 层，胜过大模型加薄壳。
5. **人是最终批准者。** 读操作自由，写操作和对外行为只生成待批准动作。批准只能发生在你面前的界面上，AI 自己没有那个按钮。

## 威胁模型（概要，详见 02）

- **邮件和消息是不可信输入。** 任何一封邮件都可能藏着给 AI 的指令。防线不是"识别注入"，而是结构隔离、输出收口、动作需批准。注入的最坏结果是一条错误的摘要，永远不是一个被执行的动作。
- **云端模型是不可信执行者。** 它看到的必须是可以被公开的内容。
- **本机被完全攻破在边界之外。** 我们不假装能防住这一层，磁盘加密和系统安全属于操作系统。

## 分身的三个阶段

| 阶段 | 名字 | AI 能做什么 | 你做什么 |
|---|---|---|---|
| 一 | 助理 | 读、整理、检索、提醒、起草 | 批准每一个对外动作 |
| 二 | 代理 | 在你预设的规则内自动执行低风险动作 | 定规则，抽查审计日志 |
| 三 | 分身 | 以你的身份对外沟通，带明确标识 | 定边界，处理它升级上来的事 |

每一阶段的前提，是上一阶段积累出足够的画像和足够长的干净审计记录。阶段之间没有捷径。

## 为什么长期成立

云端通用模型越强，模型本身越不是稀缺层。稀缺的是三样东西：数据归谁、长期上下文在哪、行动是否可控。Genatrix 做的是个人数字世界的本地操作层，模型换代不会替代它。

护城河也不是"本地部署"这个技术选择，而是用户积累多年后形成的个人数据图谱、可审计的行动历史、以及由此建立的信任关系。这三样东西只随时间增长，也只属于用户自己。所以设计上任何让数据难以迁出、难以备份的选择，都在削弱护城河而不是加固它。

## 近期非目标

P2P 网络、去中心化身份、区块链、多用户、企业部署、移动端。这些在 ESSE 时代都做过，这次全部推迟到第一阶段闭环跑通之后。

## 第一阶段只证明一件事

"全部数字生活"和"分身"都极有吸引力，也极容易让范围失控。第一阶段近乎固执地只证明一个日常闭环：

> 可信地收集 → 本地理解 → 产生有用的摘要 → 经批准完成一次行动

四个环节缺一个，闭环不成立。闭环之外的任何功能，无论多顺手，一律排到第二阶段。判断一个需求该不该进第一阶段，只问一句：它是不是这四个环节之一的必要部分。

## 第一阶段的成功标准

- 你自己每天在用它，连续三十天。
- Gmail 和 Telegram 的全部历史在本机可搜。
- 每天早上一份摘要，由本机模型生成，没有一个字节离开过这台机器。
- 至少一次，它起草的回复经你批准后发了出去，审计日志里能回放整个过程。
