## 三种记忆

借认知科学的分法，因为它正好对应三种不同的存储与信任策略。

| 记忆 | 是什么 | 在 Genatrix 里是 | 信任 |
|---|---|---|---|
| 情景 | 发生过什么 | 全部 Item。01 号已经有了 | 事实 |
| 语义 | 关于你和你的世界的知识 | 画像：人、关系、事实、承诺 | 有来源、有置信度、可撤销 |
| 程序 | 你做事的方式 | 风格：你怎么和谁说话、你的偏好 | 从你的行为中检索，不做断言 |

情景记忆不需要设计，它就是数据。本文档只讲后两种。

## 画像

画像不是一段关于你的文字，是一组带证据的结构化断言。

```
Relationship {                         // 你与一个 Person 之间
  person_id
  roles:        [标签]                 // 同事、家人、客户、律师……由你确认
  stats:        往来频率、最近往来、你的平均回复时间、常用语言   // 由数据算出，不需要确认；只算一对一往来，群里的消息不算（06 号 v0.6）
  notes:        Option<String>          // 你写的
}

Fact {                                 // 一条关于你世界的断言
  id
  subject:      person_id | self | 其他
  predicate:    String                  // "在……工作"、"生日是"、"偏好用……联系"
  object:       String
  evidence:     [Evidence]              // ItemEvidence { item_id } | UserAssertion { at }
  source:       User | Rule | Model { name, prompt_version }
  status:       Confirmed | Inferred | Rejected
  valid_from, valid_to                  // 事实会过期
}

Commitment {                           // 一个承诺
  id
  from:         person_id               // 谁答应的
  to:           person_id
  what:         String
  due:          Option<时间>
  evidence:     [item_id]
  status:       Open | Done | Cancelled | Overdue
}
```

三条规则，和 01 号对 Person 合并的态度一致：

- **每条断言必有证据。** 证据是 Item，或者是你亲口说的。你在设置里写下"我的生日是某天"，证据就是一条带时间的用户声明，界面上标为"你说的"。没有任何一种证据的事实不允许存在。这让"它为什么认为我喜欢周五开会"永远有答案。
- **模型产生的断言是 Inferred，直到你确认。** Inferred 的事实可以用在提示与起草的上下文里，界面上有标记，模型用它时提示词里也带着"这是推断"。但它不能单独成为任何自动批准规则的依据，第二阶段的规则只能建立在 Confirmed 的事实与结构性条件上。
- **拒绝会被记住。** 你拒绝了一条事实，它变成 Rejected 而不是消失。模型下次不会再提同一件事。否定记忆和肯定记忆一样重要。

## 事实如何进来

第一阶段两条路，都经过你：

- **承诺提取流水线**（03 号）抽出 Commitment，作为 Inferred 出现在"今天"页的"你答应过的"分组里。你看到了没反对，它保持 Inferred；你点确认，变 Confirmed；你说不对，变 Rejected。

  什么算承诺，宁缺毋滥。一条承诺是写信的人对另一个具体的人答应将来做一件具体的事。已经做了的事是汇报，自己的打算是计划，商家的通知是通知，都不是承诺。规则先行，模型只看剩下的：
  - 只读最近 30 天的往来。更早的承诺要么已经兑现，要么已经没有意义，挂在"未完成"里只会淹没真正要做的事。
  - 只读人与人的往来：私聊的两个方向，群里你自己说的话，邮件里带退订头、群发头或自动回复头的不读，频道不读。
  - 模型给出的承诺要有动作和对象（"周五前把报价发给 Alice"，而不是"发送"）；截止日期早于消息本身的，不算截止日期；同一个人对同一个人两周内说的同一件事只记一次。
- **remember 效果工具**，AI 在会话中觉得值得记住的，生成 WriteMemory 动作，经审批面板。

第二阶段可以给低风险事实加规则批准，比如"对方明确说出的生日"。但断言的来源永远标清楚。

## 事实如何过期

事实有 valid_to。"在某公司工作"这类会变，新的证据与旧事实矛盾时，不覆盖，生成一条待你裁决的冲突："之前记录某人在 A 公司，最近一封邮件签名显示在 B 公司"。你选一个，或者两个都保留并标时间。

沉默覆盖是画像最危险的操作，所以不存在这个操作。

## 风格

分身要"像你"，靠的不是训练，是检索。

**风格不做断言，做检索。** 起草给某人的回复时，drafter 的上下文里放的是你之前给这个人发过的三到五条消息，按相似度和时间挑。模型看到你对这个人怎么说话，照着写。这比任何"用户风格：简洁、正式"的描述都准，而且随你的变化自动更新。

有一层薄的结构化补充，从 Outbound Item 统计出来，不需要确认：

```
StyleProfile {                        // 每个 Person 一份，加一份全局
  language:        中文 | 英文 | 混合
  register:        正式 | 随意          // 由用词统计
  typical_length:  字数分布
  greeting, signoff: 常见开头和结尾
  reply_latency:   你通常多快回
}
```

它的用途是在没有足够历史消息时兜底，以及给界面上对话对象的顶部一个"你们怎么相处"的摘要（06 号 v0.5 把 Person 页改成了对话）。

## 改稿是最贵的信号

03 号定了：你改了草稿再批准，改动被记录。这里说它怎么用。

每一次改稿是一对（模型草稿，你的定稿），带 Person 和上下文。它进三个地方：

- 04 号的评测集，衡量 drafter 的质量。
- 下次给同一个人起草时的检索候选，定稿优先于历史消息。
- 长期看，如果某类改动反复出现，比如你总是把"您"改成"你"，生成一条 Inferred 的偏好事实，让你确认。

拒绝理由同样。"太长了"出现五次，就该有一条偏好。

## 记忆如何被读

recall 工具的返回是一张卡，不是一堆原文。任务涉及某个 Person 时，agent 层拿到：

```
关系卡
  你与某人：同事，往来 3 年，最近一次 2 天前，你通常 4 小时内回，用中文，随意
  已确认事实：……
  推断事实（2）：……
  未完成承诺：你答应周五前发报价
  近期往来：最近 5 条的摘要
```

卡有预算，超出就裁。裁的顺序：近期往来先裁，推断事实其次，已确认事实和未完成承诺最后。

## 遗忘

你可以删任何一条事实、承诺、关系标签。删除是 tombstone，导出时不带，模型看不到，但记录里能查到"曾经有过、被删了"。这不是为了保留，是为了让你三个月后能回答"我是不是删过这个"。

删除一个 Person 的全部画像是一个操作，删除一个来源的全部数据是另一个操作，两个都在设置里，两个都要输入确认词。

## 分身的三个阶段在这里的含义

| 阶段 | 画像的状态 | 风格的用法 |
|---|---|---|
| 助理 | Relationship 统计、Commitment 提取、少量确认过的 Fact | 起草时检索你的历史消息 |
| 代理 | Fact 积累到能回答"这个人是谁、我们的关系、有什么未了的事" | 低风险回复按规则自动发出，仍然记录 |
| 分身 | 画像足以让它代表你回应大多数日常沟通 | 以你的身份对外，**对方知道是分身** |

第三阶段有一条不可动摇的规则：对外沟通时，对方知道在和你的分身说话。用什么方式告知，到时候设计，但不告知不是选项。分身是你的延伸，不是对你的冒充。

## 明确不做

- **不做微调。** 不改模型权重来"像你"。检索加改稿信号足够，而且换模型不丢失。
- **不做"人格描述"式的画像。** 不存在一段"用户是一个……的人"的文字。画像是结构化断言加证据。
- **不做情感与心理推断。** 不记"用户情绪低落"。这类推断没有可靠证据，且被误用的代价大。
- **不做自动合并 Person。** 01 号定的。
- **不做跨用户的任何东西。** 单用户。
