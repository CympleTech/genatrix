# Genatrix · 执行器与调度

> 状态：草稿 v0.2 · 2026-11-01 · 第 3、4、11 条已裁决；其余按建议实施，待复核
> v0.2 变更：落地时的修订。宿主走管道而不是 socket；执行器说的话存进派单记录，不进 Item；派单在开始干活时就算执行完成；第二层允许命令带普通参数、允许只读的 git 命令，提交由宿主代做；第一版不做 CommentOnIssue 和 issue 入库。
> 回答的问题：需要动手的工作，比如写代码、review、跑测试，怎样交给外部的执行者去做，而数据、审批和记录仍然只归底座管。

## 为什么要这份文档

11 号的功能型 agent 没有网络、没有文件系统、没有子进程。这是对的，也不会改。

但有一类工作必须在这些东西里面做：写代码、跑测试、review、部署。这类工作已经有成熟的执行者，Claude Code、Codex 都比我们能写出来的好，而且每个月都在变好。Genatrix 不重做它们，也不该把底座往 shell 和文件系统的方向拉。

Genatrix 做它们的上游：**知道该做什么，交给谁，经你批准，结果回来记账。** 执行在边界之外，判断、审批、记录在边界之内。

这份文档从开发工作流出发，但机制不限于写代码。任何"一个外部 agent 在自己的环境里完成一件事"的场景都走这条路。

## 位置

底座内置的第三类功能是"安全地运行别人"。到现在它只有一种形态：11 号的沙箱。本文加第二种：

| | 功能型 agent（11 号） | 执行器（本文） |
|---|---|---|
| 在哪运行 | 核心里的 WASM 沙箱 | 边界之外，单独的系统身份 |
| 能碰什么 | 只有核心开的口子 | 它自己的工作目录、网络、shell |
| Genatrix 管得住什么 | 它的一切 | 它拿到什么、它做成的东西怎样变成对外效果 |
| 信任 | 不可信代码，被关住 | 不可信执行者，和云端模型同一类 |
| 谁写的 | 你、朋友、我们 | 厂商：Anthropic、OpenAI…… |

诚实地说清楚：**Genatrix 管不住执行器在它自己的工作目录里做什么。** 它是一个能执行命令、能联网的程序，背后是一家云服务。Genatrix 能管住、而且必须管住的是三件事：

1. **它拿到什么。** 交给它的每一段文字都经过出境闸门。
2. **它碰不到什么。** 核心的数据、密钥、你的账号凭据，它在操作系统层面就读不到。
3. **它做成的东西怎样出去。** 推送、开 PR、合并、发消息，都是待批准动作，由连接器执行，执行器手里没有这些操作的凭据。

02 号的信任分区多一个区：

| 区 | 谁 | 信任程度 | 能看到什么 |
|---|---|---|---|
| 6 | 执行器 | 不可信执行者 | 派单放行的文字，和你为这个项目交给它的代码仓库 |

## 概念

```
Executor   一个执行者。Claude Code、Codex。通过 ACP 驱动，有身份、能做的事、背后的厂商。
Project    一个项目。一个代码仓库，允许哪些执行器碰它，检查命令，分支规则。
Role       一个角色。产品、UI、前端、后端、测试、运维。一段提示词加一组权限，不是一个进程。
Recipe     一个流程模板。哪一步由哪个角色、哪个执行器来做，产出什么，最多几轮，何时停。
Dispatch   一次派单。模板加任务描述加范围加预算。它是一个待批准动作。
Session    一次执行器会话。属于某次派单的某一步。
Artifact   一步的产出。一组提交、一份 review 意见、一份测试报告、一份需求说明。
```

### 角色不是进程

六个角色不意味着六个常驻的 agent。一个角色是一段提示词、一组允许的操作和一种产出物。派单的某一步需要"后端"，核心就用后端这个角色的提示词和权限，起一个执行器会话，做完即止。

| 角色 | 产出 | 第一版的执行器 | 第一版做到哪 |
|---|---|---|---|
| 产品 | 需求说明 | Claude Code | 产出文档，你批准后作为下一步的输入 |
| UI | 设计说明、组件草图 | Claude Code | 同上 |
| 前端 | 提交 | Claude Code | 在工作区里改代码、跑检查 |
| 后端 | 提交 | Claude Code | 同上 |
| 测试 | 测试代码、测试报告 | Codex | 写测试、跑测试、报告 |
| 运维 | 变更计划 | Codex | **只提议，不执行部署** |

哪个角色用哪个执行器，是模板里的一行，不是写死的。

### 协作经过核心

角色之间不直接对话。Codex 的 review 意见是一个 Artifact，回到核心，入库，下一步的模板把它装进信封交给 Claude Code。这样：

- 每一次交接都有记录，可以回放；
- 每一次交给执行器的文字都过闸门；
- 执行器之间没有一条核心看不见的通道。

这和 11 号"不做 agent 之间直接通信"是同一条原则：要协作，经过核心。

## ACP

执行器通过 ACP（Agent Client Protocol）驱动：JSON-RPC，走子进程的标准输入输出。**Genatrix 是客户端，执行器是 agent。** Claude Code 和 Codex 目前都通过适配器接入。

选它的理由：

- **它本来就是"一个客户端驱动若干编码 agent"。** 不用为每个执行器写一套驱动。
- **它把权限请求交还给客户端。** 执行器要写文件、跑命令之前，发 `session/request_permission`，由客户端决定。这一点让"范围内自主"有了落点，见下一节。
- **会话过程是结构化的流。** 计划、工具调用、文本，都能按类型记录，而不是一大段终端输出。

三条做法：

- **核心不向执行器提供文件和终端能力。** ACP 允许客户端替执行器读写文件、开终端。Genatrix 一项都不声明。执行器用它自己的工具，在它自己的工作区里做事。核心的文件系统不是它能借的东西。
- **核心不向执行器提供任何数据通道。** 不给它装一个能查你邮件的 MCP。执行器要的上下文，全部写进派单，过闸门。以后真要开，是一个有读范围的口子，每次调用都是一次出境，另立文档。
- **执行器层的 MCP 由你在执行器里自己装。** 某个项目要连某个服务，在 Claude Code 里配。Genatrix 不管，也不为它担保。

## 两层批准

如果执行器每写一个文件都弹一张卡片到你手机上，一个小时就是上百张。那是 11 号说的审批疲劳，等于没有审批。所以分两层。

### 第一层：派单

你批准的是一次派单。卡片上写：

- 项目、模板、每一步由谁来做；
- **交给执行器的全部文字**，也就是这次出境的内容，脱敏之后的那一版；
- 范围：工作区、允许的命令、能不能联网装依赖；
- 预算：墙钟时间、最多几轮、费用上限。

你可以改任务描述再批准，改了就是新版本，和 03 号一样。

### 第二层：范围内自主

派单批准之后，执行器在范围内自己干活。它发来的每一个权限请求，由核心按批准的范围回答：

| 请求 | 回答 |
|---|---|
| 在工作区内读写文件 | 允许 |
| 运行项目声明过的命令（测试、构建、检查） | 允许 |
| 工作区以外的路径 | 拒绝 |
| 没声明过的命令 | 拒绝 |
| 只读的 git 命令（status、diff、log、show） | 允许，评审要看改动 |
| 改自己的模式（比如关掉自己的权限询问） | 拒绝 |
| 推送、改远程、碰凭据 | 拒绝，而且它本来也没有凭据 |

"声明过的命令"包括在它后面加普通参数：声明了 `cargo test`，`cargo test -p x` 也算；但只要出现分号、管道、重定向、`$()` 这类能接第二条命令的符号，就不算。

执行器不自己提交。一步结束时，宿主把它留在工作区里的改动提交掉，提交信息写明是哪一步。这样 `git commit` 不必放进它能运行的命令里。

范围外的请求**拒绝，不转给你**。转给你等于把审批疲劳从卡片换到了弹窗。执行器被拒绝后自己想办法，想不出来就在产出里说明，由你决定下一次派单要不要扩大范围。

这一层只在执行器遵守协议时成立。一个被注入的执行器可以不问就做。所以它下面还有一层操作系统的隔离，见"本机隔离"。

### 第三层其实是老规矩：对外效果

工作区里的提交是草稿，不算对外。真正离开这台机器、影响别人的，都是 03 号的 Action：

| Action | 执行者 |
|---|---|
| PushBranch | 代码托管连接器 |
| OpenPullRequest | 代码托管连接器 |
| CommentOnIssue | 代码托管连接器（第一版不做，等 issue 入库之后） |
| SendMail、SendMessage | 现有连接器 |

推送的卡片绑定到具体的提交哈希。你批准的是"这几个提交"，不是"这个分支"。执行器之后又改了什么，是新的提交，要新的批准。

合并和部署第一版不做，见"明确不做"。

## 流程模板

模板是声明式的文件，短到一屏能读完，和 11 号的清单同一种写法。它是这次协作**全部**会发生的步骤。

```
name    实现并评审
steps
  1  实现     角色 后端   执行器 claude-code   产出 提交
  2  评审     角色 测试   执行器 codex         产出 评审意见（通过 | 需要修改）
  3  修改     角色 后端   执行器 claude-code   输入 评审意见   产出 提交
     2 与 3 循环，评审通过或满 2 轮为止
  4  提议     核心        生成 PushBranch 与 OpenPullRequest，等你批准
```

规则：

- **模型只能选模板、填参数。** 它不能在运行中加一步、换执行器、改循环上限。这是 03 号"不做自主调度"在多执行器上的落地。
- **循环有上限，写在模板里。** 两个执行器互相说服对方可以无限进行下去，上限防的就是这个。
- **步骤之间的判断是结构化的。** 评审给出"通过"或"需要修改"加意见，模板按枚举走，不由一段自然语言决定下一步。
- **模板是版本化的文件，hash 就是身份。** 新增或修改模板是一个待批准动作。12 号的演化可以提议改模板或角色的提示词，同样经你批准。
- **触发和 11 号一样只有三种：** 你说一句话；项目范围内有新 Item（比如一个打了标签的 issue）；模板里写死的日程。触发产生的是派单草稿，不是派单。第一版只有第一种：GitHub 的 issue 还没有入库，日程也还没有。

## 调度

把"你的一句话"或"一个 issue"变成一张派单卡片，需要理解：该用哪个模板、任务怎么写、要附上哪些上下文。这是调度。

- 调度是一次模型调用，目的是 02 号枚举里的 Plan。它的产出是一个 Pending 的 Dispatch，不是派单本身。
- 本机模型做不好时，可以用云端，最早在第二阶段云端打开之后（见待裁决第 11 条）。用云端照常过闸门：算级别、查策略、脱敏、记账。云端默认关，按目的单独开。在那之前，调度由本机模型起草，起草得不好，你在卡片上改。
- **第一版没有自动派单。** 每一次派单都经你批准。第二阶段的规则批准将来能不能用在派单上，另议；扩大范围的派单永远不能。

## 派单就是出境

把一封客户邮件里的 bug 描述交给 Claude Code，就是把这段文字送到了 Anthropic。所以：

- **交给执行器的每一段文字都经过出境闸门。** 派单的第一条 prompt、模板里每一步的后续 prompt、交接给下一步的 Artifact，无一例外。级别按引用的 Item、Artifact 和你写的文字取最高。
- **目的是新的一项：Delegate（交给执行器）。** 02 号说过新目的先进枚举再定策略，不存在"其他"。调度用 Plan，交给执行器的文字用 Delegate，两者分开开关。
- **执行器是云端目标。** 每个执行器在注册表里标明它背后的厂商，策略矩阵对它和对云端模型一样：Secret 不出；Personal 要云端已开、这个目的允许、脱敏之后才出。派不出去的派单，卡片上写明原因。
- **凭据绑定字节。** 闸门签发 02 号的 EgressTicket，目标是这个执行器。执行器宿主（见下）发送前核对哈希，没有凭据、凭据不符的内容不发。这是 02 号"两层执行"在执行器上的第二层。
- **代码仓库不是 Item，不经闸门。** 把一个仓库交给哪些执行器，是你在建项目时做的决定，属于高权限操作。项目页写明"这个仓库对 Anthropic、OpenAI 可见"。

## 本机隔离

执行器能执行命令。一个读了恶意 issue 的执行器，会照着 issue 里的话去做。所以它在操作系统层面要和核心隔开。

**执行器以单独的系统用户运行。** 它的工作区在这个用户名下。它读不到核心的数据目录、读不到你的钥匙串、没有你的 git 推送凭据和 SSH 密钥。

**代码怎么进出。** 核心为项目维护一份镜像，执行器的用户能读、不能写；核心以执行器的用户把镜像克隆到它自己的工作区，删掉其中的远程地址；执行器在里面干活；做完以后，新提交打成一个 git bundle 交回核心。核心核对它确实接在出发的那个提交之后，把它归档在镜像里一个自己的引用下，出卡片。推送由代码托管连接器用你的凭据完成，执行器从头到尾碰不到这些凭据。

**回环不再等于你本人。** 这是本文对现有设计最大的修订。06 号和 02 号第 11、12 条把回环当成"已经在这台机器上的人"，不需要任何凭据，可以批准动作，可以装 agent。这在只有你一个人用这台电脑时成立；一旦这台电脑上有一个会执行命令的 AI，它用一行 `curl` 就能批准自己的推送。

修订后，"本机"的判据从网络地址换成凭据（已裁决，02 号 v0.3、06 号 v0.11）：

- 核心在数据目录里放一个只有你的系统用户可读的随机密钥。本机请求是来自回环、并且带着它的请求。
- 菜单栏壳读这个文件，打开页面时带上；浏览器由 `genatrix open` 给一个一次性链接，换到这个密钥作为 cookie。命令行本来就直接读数据目录。
- 回环地址本身不再给任何权限。执行器的系统用户读不到那个文件。

这一条在任何执行器运行之前就要落地。

## 宿主

执行器宿主是核心为每一步启动的一个进程，地位和 05 号的连接器一样，以你的系统用户运行。它和核心之间走它自己的标准输入输出：这两根管道只有核心拿着，所以不需要 socket，也不需要令牌。它只做三件事：

1. 以执行器的系统用户启动执行器进程，用 ACP 驱动它；
2. 只发送带有效出境凭据的文字；按派单批准的范围回答权限请求；
3. 把会话流和产出交回核心。

它不理解内容，不调模型，不做判断。判断在核心。

代码托管连接器（第一个是 GitHub）也是一个进程，但一次只做一件事：核心为每一个批准过的推送或 PR 启动它一次，经标准输入把这一次要用的 token 交给它，它做完就退出。它在沙箱里，只能连 443 端口，读不到数据目录和钥匙串文件。推送之前它再核对一遍：镜像里归档的提交，必须正是你批准的那一个。

派单这个动作在工作开始时就算执行完成。批准它，批准的是"开始这项工作"；一项工作可能要跑一个小时，比一个动作等待回报的时间长得多。此后工作进行得怎样，看这次派单自己的记录。

## 记录

每次派单是一个 Run，发起者是这次派单；每一步的会话是 Run 里的 Step。

- 执行器的会话流（它的计划、它调了什么工具、它说了什么、它请求了什么权限、得到什么回答）按步存进这次派单的记录，级别是这次派单的级别。它是外面的人写的东西，和邮件正文一样是不可信输入。它不进 Item：它不是你生活的一部分，不该出现在时间线、每日摘要和检索里。
- 运行记录只存引用，03 号的规则不变。
- 出境记录里有每一段交给执行器的文字，和交给云端模型的一样。
- 产出的提交以 bundle 的哈希入库。

## 不可信输入

执行器的输出和邮件正文同等对待：

- 存进派单的记录，不进 Item；交给下一步时装进信封；
- 不能成为 12 号一条课的证据，课的证据只能是你的行为；
- 不能触发新的派单。一个执行器在产出里写"接下来请派一个部署任务"，那只是一段文字。

## 界面

06 号要加的：

- **项目页。** 仓库、允许的执行器、它们背后的厂商、检查命令、模板列表、最近的派单。
- **派单卡片。** 按固定模板渲染：上面列出的全部字段，出境的文字放在最显眼处。
- **进行中的派单。** 每一步的状态和会话流，只读，可以随时停止。停止就是终止执行器进程，产出到此为止。
- **推送卡片。** 提交列表、改动统计、可以点开的差异、评审结论。

## 不变量（提议，通过后并入 02 号）

22. 交给执行器的每一段文字都经过出境闸门，带一张与其字节哈希一致、未过期、未用过的凭据；执行器宿主不发送没有凭据或凭据不符的内容。
23. 执行器以独立的系统用户运行，读不到核心的数据目录、密钥文件、钥匙串中的凭据，以及你的代码托管凭据。
24. 执行器的对外效果（推送、开 PR、评论、发消息）只以待批准动作出现，由连接器执行；推送的批准绑定到具体的提交哈希。
25. 执行器在会话中请求的权限，由核心按这次派单批准的范围回答，范围外一律拒绝。
26. 流程模板和角色由你提交或经批准生效；模型只能选择模板、填写参数，不能在运行中增加步骤、更换执行器或改变循环上限。
27. 执行器的输出是不可信输入：它不能触发派单，不能成为课的证据。
28. 本机身份不由网络地址认定。（已随裁决第 4 条并入 02 号 v0.3 的第 11、12 条：本机请求是来自回环、并且带着只有核心的系统用户可读的本机凭据的请求。）

## 明确不做

- **不打包执行器。** Claude Code、Codex 由你自己安装和登录，Genatrix 只驱动它们。登录是执行器用户自己的：它没有桌面，打不开浏览器，也没有钥匙串，所以 Claude Code 用你本人 `claude setup-token` 生成的长期 token，经标准输入交给 `sudo`，存在执行器用户 home 下的 `~/.genatrix/<执行器>.env`，只有它能读；执行器启动时由它自己的 shell 读入环境变量。宿主和核心都不持有这个 token。
- **不给执行器数据通道。** 不向执行器提供能查 Genatrix 数据的 MCP 或接口。它要的上下文全在派单里。
- **不向执行器提供文件和终端能力。** ACP 里这两项核心一项都不声明。
- **第一版不做合并和部署。** 运维角色只产出变更计划。部署是影响面最大的对外效果，等推送和 PR 的审批跑稳了再谈，到时候另立文档。
- **执行器之间不直接通信。** 协作经过核心。
- **第一版不做自动派单。**
- **不管执行器层的 MCP。** 你在执行器里装什么，是你和它之间的事，Genatrix 不为它担保。
- **不做团队协作。** 一个人，自己的项目。00 号与 11 号的定位不变。
- **不让执行器碰底座。** 执行器可以在它的工作区里改 Genatrix 自己的代码，那是一个项目而已；改动生效的方式和任何项目一样：推送、你 review、你合并、你构建。
