# Genatrix · 连接器

> 状态：草稿 v0.2 · 2026-09-13 · 已通过（2026-09-14）
> v0.2 变更：能力由核心签发、由沙箱执行；隔离粒度的诚实表述；Source 复合 id 的构成；SMTP 的未知态；执行前逐项校验。
> 回答的问题：邮箱和 Telegram 如何以普通用户能用的方式接进来，如何可靠地持续同步，如何执行被批准的动作。

## 连接器是什么

连接器是 Genatrix 与一个外部系统之间的全部接触面。它做三件事，只做三件事：

1. 把源系统的对象原样拉回来，变成 Raw，再归一成 Item。
2. 持续同步，断了能续，续上不漏不重。
3. 执行状态为 Approved 的 Action，并把执行结果作为 Item 回流。

它不理解内容，不做判级，不调模型。它是搬运工，不是判断者。

## 进程模型

每种连接器一个进程，一个进程可以服务多个账号。

```
genatrix-imap        所有邮箱账号
genatrix-telegram    所有 Telegram 账号
```

核心是服务端，连接器是客户端，通过 unix socket 连入。协议是长度前缀的 protobuf，形状借 crabtalk 的 proto，不借它的依赖。

分进程隔离的是连接器种类，不是账号。IMAP 连接器崩了，Telegram 不受影响；但 IMAP 连接器的依赖库有漏洞，泄露的是全部邮箱账号的凭据，不只是一个。这是一个有意的取舍，换来的是进程数可控。如果以后某个用户接了十个邮箱，升级路径是每账号一个受限的子进程，协议不变。

能力不是连接器自己声称的，是核心签发的。接入一个账号时，核心根据用户批准的配置生成这个账号的能力：

```
AccountCapability {
  connector:     "imap" | "telegram"
  account:       账号标识
  hosts:         [允许连接的主机与端口]     // IMAP、SMTP 或 Telegram 数据中心
  can_execute:   [Action kind]
}
```

连接器进程启动时拿到它负责的全部账号的能力，进程的沙箱按这些能力的并集配置。SMTP 提交服务器是能力的一部分，不能漏。

沙箱能保证什么、不能保证什么，要说准确。macOS 的沙箱按端口过滤出站连接，不认主机名：它不做域名解析，而 `imap.gmail.com` 背后的地址会变。所以操作系统保证的是"只能连能力里出现的端口"（IMAP 的 993、SMTP 的 587 或 465），其余端口一律拒绝；"只连自己的源服务器"这一层主机名检查由连接器自己做，是第二层。一个被攻破的连接器能连到别的 993 端口，连不到任何别的端口。这比"操作系统保证只连源服务器"弱，但它是真的。域名解析走系统解析器的 socket，核心的 socket 按目录放行。

核心启动连接器时在环境变量里给它一枚一次性令牌，连接器连入时出示。核心只接受带当前令牌的第一次问候，之后的连入一律拒绝。这防的是同一用户下的别的进程连上 socket 索取凭据；它不防已经能读核心进程内存的对手，那在 08 号的威胁模型之外。凭据在问候的应答里过去，连接器不落盘、不记日志。

## 生命周期

每个账号独立经历四个阶段。

### 接入

用户提供凭据，连接器验证，凭据进钥匙串，账号的 Handle 挂到 `is_self` 的 Person 上。接入流程的界面在 09 号，这里只定协议：连接器提供一个"验证凭据"的接口，成功返回账号标识与自我 Handle，失败返回人能看懂的原因。

### 回填

历史数据导入。**从最新往最旧**，不是反过来。理由是产品的：接入后五分钟，时间线上就该有这周的东西可看可搜，而不是 2015 年的邮件。

回填有进度，界面可见："已导入 3,240 / 约 48,000 封，当前到 2024 年 3 月"。回填可以暂停、可以在任何时刻中断，下次从断点继续。

回填的速度受源系统限流约束，连接器负责退避，不负责突破。

### 实时同步

回填进行中或完成后，实时同步同时运行。新东西到达，几秒内入库。

### 恢复

连接断了、机器睡了、密码改了、会话被吊销了。连接器把错误分成三类，向核心报告，核心决定呈现：

| 类别 | 例子 | 处理 |
|---|---|---|
| 瞬时 | 网络抖动、服务器 5xx、限流 | 指数退避自动重连，用户无感 |
| 需要用户 | 密码变更、两步验证、会话被吊销 | 停止该账号，界面上一个明确的"需要重新登录"，一步完成 |
| 永久 | 账号被删、服务器不存在 | 停止，说明原因，保留已有数据 |

## 幂等与检查点

不漏不重靠两样东西。

**幂等**靠 01 号的 Source 三元组。同一个源对象拉两次，第二次跳过。这让"宁可多拉"成为安全策略：怀疑漏了，就重拉一段，不会重复入库。

**检查点**是每个账号、每个子空间的同步游标，存在核心里，由连接器更新：

| 连接器 | 子空间 | 游标 |
|---|---|---|
| IMAP | 每个文件夹 | UIDVALIDITY 加最高已同步 UID |
| Telegram | 整个账号 | 更新序列号（pts、qts、date） |

游标失效的处理是确定的：IMAP 的 UIDVALIDITY 变了，该文件夹全量重扫，幂等保证不重；Telegram 更新序列出现空洞，调差量接口补齐，补不齐就对受影响的对话重扫最近一段。

## 邮箱：IMAP

### 为什么是 IMAP

00 号定的：普通用户不会去创建 OAuth 开发者凭据。IMAP 加应用专用密码，Gmail、Outlook、iCloud、QQ、163 都支持，一套连接器覆盖所有邮箱，这是 IMAP 的第二个好处。

代价是 Gmail 需要用户先开两步验证再生成应用密码，步骤在 Google 的设置页里，路径不直观。09 号的接入流程要用截图一步一步带着走。另一个风险是 Google 可能进一步限制应用密码，这在 10 号风险清单里。

### 自动配置

用户只输邮箱地址和应用密码。服务器地址、端口、加密方式由连接器推断：先查主流域名的内置表，再试自动发现协议，最后才让用户手填。目标是九成用户不需要看到"服务器地址"四个字。

### 拉取

- 优先用 Gmail 的 IMAP 扩展：线程 id、消息 id、标签。有就用，没有就退到标准 IMAP。
- 对 Gmail 只同步"所有邮件"一个文件夹。已发送的邮件也在里面，"已发送"只是一个标签视图，再读一遍是白拉；草稿和垃圾邮件不是往来，不读。标签作为 Item 的载荷属性。
- 对标准 IMAP 同步除草稿、垃圾邮件、已删除之外的全部文件夹，文件夹名进载荷。
- 消息标识：优先 Gmail 的消息 id；没有就用 `Message-ID` 头；两者都没有才退到"文件夹/UIDVALIDITY/UID"。前两种在文件夹重编号后不变，重扫时靠它们去重；只有第三种在重编号后会再入一次，这是"不重"唯一的漏，接受。
- 实时同步用 IDLE，服务器不支持就每分钟轮询。IDLE 醒来或超时后都做一次"检查点以上有没有新 UID"的查询，这个查询很便宜，所以两种服务器走同一条路。
- 回填和实时同步共用一条连接，轮流进行：每一轮先取所有文件夹的新邮件，再取一批历史。回填期间新邮件最多等一批的时间；回填完成后连接转入等待。第一次看到一个文件夹时不拉任何东西，只把实时游标定在最新一封、历史游标定在顶端，从第一轮起就是从新到旧，每封只拉一次。
- 每个文件夹两个游标：实时游标（UIDVALIDITY 加最高已同步 UID）和历史游标（UIDVALIDITY 加已到达的最旧 UID、是否到底）。两个都存在核心里，每批之后、先存邮件再存游标，中断只会多拉一批，不会漏。

### 归一

- 原始 RFC 822 字节进 Raw，一个字节不动。
- Source 的 external_id：Gmail 用它的全局消息 id；其他服务器用"文件夹 + UIDVALIDITY + UID"。Message-ID 头只作辅助去重，它可以重复也可以缺失。
- 线程：Gmail 有线程 id 直接用；否则按 References 和 In-Reply-To 重建，再退到主题归一加时间窗口。
- 正文：优先取纯文本部分；只有 HTML 时转纯文本，剥掉样式、脚本、跟踪像素；剥掉引用的上一封。剥引用的规则保守，宁可多留不可误删。
- 附件进 Blob，内容寻址。内嵌图片也是 Blob。
- 发件人、收件人、抄送映射到 Handle，第一次出现自动建 Person。
- direction 按 from 是否是自我 Handle 判定。

### 发送

Action 为 SendMail 时，通过 SMTP 提交端口发送，凭据同一个应用密码。发送成功后，把发出的邮件作为 Outbound Item 入库，Action 记录它的 id。Gmail 会自动把它放进"已发送"，下一次同步会拉到同一封，幂等跳过。

提交后连接中断、没收到服务器的最终应答，结果是 Unknown，不是 Failed。Action 进入 Unknown 状态，界面告诉你"可能已发出，等待同步确认"，下一次同步在"已发送"里看到它就转为 Executed，看不到就由你决定。绝不能让一个模糊的失败诱使用户再点一次。

回复要带正确的 In-Reply-To 和 References，否则对方的客户端不会把它归到同一个线程。这是最容易被忽略又最影响体面的细节。

## Telegram：用户账号协议

### 为什么是用户协议而不是 Bot

Bot 只能看到发给它的消息。你自己的 Telegram 历史，只有以你的身份登录才拿得到。这是 00 号的"全部数字生活"在这里的唯一可行路径。

用 Rust 的 MTProto 客户端库实现。登录流程和手机上装 Telegram 一样：手机号、收验证码、如果开了两步验证再输密码。会话（含授权密钥、已知对话缓存、更新序号）序列化后存在核心的加密库里，与同步游标同表；它受钥匙串里主密钥的保护，和放钥匙串等价，而对话缓存有几十万字节，钥匙串不是放它的地方。原文说"会话密钥进钥匙串"，实现按此修正。

沙箱对 Telegram 连接器的约束比对邮件弱，要说明白：Telegram 走 443 端口，按端口过滤的沙箱等于放行到任何主机的 443。数据中心地址写在能力里，由连接器自己检查；操作系统只保证它连不到别的端口、读不到数据目录和钥匙串、起不了别的进程。

### 应用凭据

Telegram 要求每个客户端程序持有一对应用凭据。Genatrix 作为一个应用申请一对，编译进程序，所有用户共用。这是 Telegram 允许的做法，所有第三方客户端都这么做。风险是所有 Genatrix 用户的流量在 Telegram 眼里来自同一个应用，个别用户的滥用可能影响整体。缓解是连接器保守地遵守限流，不做任何批量或自动化的对外行为。这一条在 10 号风险清单里。

### 拉取

- 先拉对话列表，得到全部 Thread。私聊、群、超级群、频道分别映射到 01 号的 DirectChat、GroupChat、Channel。
- 每个对话从最新往最旧翻消息，游标是消息 id。全部对话并行翻，受限流约束。
- 翻多远分两种：私聊翻到底，那是你自己的往来；群和频道只翻最近三十天，之后靠实时更新往前走。一个人待过的群加起来动辄几十万条，绝大部分与他无关，全量导入既撑大数据库，也让判级和向量化在别人的闲聊上烧几个小时。三十天是默认值，以后按对话可调。
- 实时更新走长连接，按更新序列号处理，空洞按前文补齐。
- 消息的原始结构序列化后进 Raw。

### 归一

- Source 的 external_id：chat id + message id。消息 id 只在群与频道内唯一，单独用会撞。
- 文本消息：格式实体展平成纯文本，链接保留 URL。
- 媒体：图片、文件、语音、视频进 Blob。**媒体下载策略**：小于一个阈值的立即下载，大的先记元数据，用户点开时再取。阈值默认 10 MB。语音消息的转写不在第一阶段。
- 转发：forwarded_from 指向原作者的 Person。
- 回复：reply_to 指向被回复的 Item。
- 编辑：新 Item supersedes 旧的。删除：tombstone。这是 01 号定的。
- 公开频道默认 Public，其他默认 Personal，是 02 号规则的输入。

### 拿不到的

秘密聊天是端到端加密且绑定设备的，Genatrix 作为另一个登录设备看不到。这是协议的性质，不是我们的缺陷，界面上要说清楚。

### 发送

Action 为 SendMessage 时，向目标对话发送文本。发送成功后消息以 Outbound Item 入库。第一阶段只发文本，不发媒体。

## 动作执行

连接器只接受 Approved 状态的 Action，从核心拉取，不是核心推送。执行前逐项校验：状态 Approved、未过期、一次性执行令牌有效、目标账号属于本连接器且能力允许该 kind、要发送的版本哈希与批准的版本一致。任何一项不符，拒绝执行并记录。

执行结果四种：成功并回流 Item；失败并附原因，Action 变 Failed，不重试，交给用户决定；目标不存在，同 Failed；提交后结果不明，Unknown，等待同步确认。

**永远不自动重试发送。**一封邮件发两遍比发失败糟得多。

## 状态呈现

每个账号有一个状态，界面上一眼可见：同步中、已同步、暂停、需要重新登录、错误。加上最后同步时间和回填进度。06 号定形态。

## 明确不做

- **不做 OAuth。** 00 号定的。
- **不做 Telegram Bot API。** 它是聊天入口，不是数据来源。以后要做"通过 Telegram 和 Genatrix 对话"，另开一个入口类连接器。
- **不做微信。** 没有可用的协议，做了也是随时会断的黑魔法。
- **不做日历、Exchange、Outlook 专有协议。** 第二阶段。
- **不做语音转写。** 第二阶段，且必须本机。
- **不做多设备之间的连接器状态同步。** 单设备。

## 与后续文档的接口

- 01 号：Source、Raw、Item、Thread、Person 的映射。
- 02 号：hosts 声明；来源级默认级别的输入；凭据入钥匙串。
- 03 号：Action 的执行与回流。
- 06 号：账号状态、回填进度、重新登录的呈现。
- 08 号：检查点的存储；Blob 的落盘。
- 09 号：接入流程；自动配置的用户体验；恢复时的一步重登。

## 已裁决（2026-09-14，全部按建议通过）

1. 每种连接器一个进程，多账号共用。我主张这样。
2. 回填从最新往最旧。我主张这样。
3. Telegram 使用 Genatrix 统一的应用凭据。别无选择，但要你知道风险。
4. 媒体大于 10 MB 延迟下载。阈值可议。
5. 发送永不自动重试。我主张永不。
