# Genatrix · 存储与加密

> 状态：草稿 v0.2 · 2026-09-13 · 已通过（2026-09-14）
> v0.2 变更：算法与派生写死；密钥版本与轮换；恢复密钥的定义；账本链的排序与链头；数据目录不被索引与同步。
> 回答的问题：本机数据如何落盘、如何加密、如何保证能迁出，以及加密到底防的是什么。

## 加密防什么，先说清

加密落盘防三件事：磁盘被拿走、备份被拷走、数据目录被同步到某个云盘。这三种情况下，没有钥匙串里的主密钥，数据是密文。

它不防一件事：同一个用户账号下运行的恶意程序。那样的程序可以像 Genatrix 一样向钥匙串要密钥。这是 00 号威胁模型里"本机被攻破在边界之外"的具体含义。不说清这一点，加密就成了虚假的安全感。

## 目录

遵循 macOS 的约定，全部在一个目录下，卸载时删这一个目录加钥匙串里的几项，就干净了。

```
~/Library/Application Support/Genatrix/
  config.toml           配置。不含任何凭据
  rules/                敏感分级规则，yaml，用户可读可改
  data.db               主库：Item、Thread、Person、Annotation、画像、检查点
  ledger.db             账本：出境记录、运行记录、动作记录。只增不改
  raw/                  原始记录，内容寻址，逐文件加密
  blobs/                附件体，内容寻址，逐文件加密
  models/               模型权重。不加密，不是个人数据
  eval/                 评测集。加密
  export/               导出的目标目录，默认位置
```

数据目录标记为不参与 Spotlight 索引，不参与 iCloud 的桌面与文稿同步，Time Machine 除外。导出目录由用户选择，导出时提醒不要选在会被同步的位置。诊断包（09 号）不收集这个目录下的任何文件内容。

## 为什么是 SQLite

单用户、单设备、单进程写入。SQLite 是这个场景的正确答案，不需要论证。需要论证的是为什么不用别的：

- 不用 Postgres。多一个服务进程，普通用户装不起来。
- 不用 crabtalk 的 crabdb。零测试，无加密，无生态工具。它的存储抽象设计值得借，引擎不借。
- 不用向量专用数据库。sqlite-vec 扩展够用，规模是几十万条不是几十亿。

## 两个库

主库和账本分开成两个文件，理由是 02 号：账本只增不改，agent 层没有写权限。分文件让这条规则由文件权限和连接方式保证，不只靠代码纪律。

**data.db** 用 SQLCipher 整库加密。表结构直接映射 01 号的实体，加画像和检查点。

**ledger.db** 同样 SQLCipher。一张只增的记录表，用 kind 字段区分三类记录：出境、运行、动作。状态变化不是修改，是新记录：一次出境的发送结果、一个动作的每次审批与执行，各是一条引用前一条的新记录。用触发器禁止 UPDATE 和 DELETE，借 finance 项目"触发器级防篡改"的做法。核心里只有闸门和 agent 运行器持有它的写连接。

一张表而不是三张，理由是哈希链。链要跨越全部记录连续编号，三张表就得共享一个序号来源，一张表天然就是。

账本里每条记录带前一条记录的哈希，形成一条链。写入是串行的：一个写入队列，序号由队列分配，链按序号而不是按时间戳，并发写入不会产生分叉。链头存在库外的一个小文件里，自检时从链头往回验到根。这不是为了对抗攻击者，攻击者拿到密钥能重写整条链和链头。它是为了让"记录有没有被改过"变成一个可以用一条命令回答的问题，对付的是 bug 和误操作，不是敌人。外部锚定不做，那是企业场景的事。

## 密钥

```
主密钥        随机生成，256 位，存 macOS 钥匙串，随登录解锁
库密钥        HKDF-SHA256(主密钥, "genatrix/db/v1")，SQLCipher 用
文件密钥      HKDF-SHA256(主密钥, "genatrix/file/v1" ‖ 文件哈希)，每个文件一把
```

算法写死，实现时不留选择空间：

- 逐文件加密用 XChaCha20-Poly1305，每个文件一个随机 24 字节 nonce，存在文件头。
- 密钥派生用 HKDF-SHA256，info 字段带用途与版本。
- 口令包装主密钥用 Argon2id，参数取当前推荐值并随版本升级。
- 每个加密对象带一个版本字节，指明它用的算法与派生方式。将来换算法按版本解，不需要猜。

**轮换。** 主密钥可以轮换：生成新主密钥，逐文件重加密在后台进行，版本字节区分新旧，库密钥随 SQLCipher 的 rekey 更换。触发轮换的场景是恢复密钥可能泄露，用户在设置里一键。

只有一把东西需要保护，就是钥匙串里的主密钥。备份时，主密钥不在数据目录里，这是设计意图：拷走目录拿不到数据。

**恢复密钥**是主密钥的另一份副本，用可抄写的编码呈现，只在用户请求时生成并展示一次。它和主密钥等价，能打开一切。它不出现在日志、诊断包、界面的可复制区域，也不落盘。快照文件带足够的密钥包装元数据，使"快照 + 恢复密钥"足以在新机器上恢复，不依赖旧机器的任何东西。

用户可以选择设置一个口令，主密钥在钥匙串里用口令再包一层。设了口令，Genatrix 启动时要输入。恢复密钥不受口令约束，持有它就等于持有主密钥，展示恢复密钥时要明说这一点。默认不设口令，因为普通用户会忘，忘了就是全部数据丢失。这个默认在 09 号的首次运行流程里要解释清楚。

## 逐文件加密

raw 和 blobs 目录下的文件名是内容哈希，内容用文件密钥以带认证的流加密算法加密。为什么不放进 SQLite：附件可能几百 MB，数据库里放大对象会让整库备份和 VACUUM 变慢，而且内容寻址天然去重，放文件系统更自然。

文件名是明文哈希这件事泄露的信息是"有没有某个已知文件"。接受，威胁模型里没有这种对手。

## 全文检索

SQLite FTS5。分词器是难点：默认的 unicode61 不会切中文。

第一阶段用 trigram 分词器。它对中文、日文、任何语言都能做子串匹配，索引体积大约是原文的三倍，可接受。它的缺点是相关性排序粗糙。第二阶段再评估中文分词器，比如 jieba 的 Rust 实现做自定义分词，前提是先有评测数据证明 trigram 不够。

向量检索用 sqlite-vec。向量存在 Annotation 表里，索引在同一个库。

## 迁移

Schema 版本号存库里。迁移只向前，每个版本一个 SQL 文件，启动时按顺序执行。

迁移失败的恢复策略是 01 号三层设计给的：Raw 永不修改，所以任何 Item、Annotation 的迁移失败都可以从 Raw 重建。迁移前自动做一次库文件快照，失败就回滚到快照。

## 备份

三种，从轻到重：

| 方式 | 内容 | 用途 |
|---|---|---|
| Time Machine | 整个数据目录，密文 | 零配置，用户已经在用 |
| 导出 | 01 号的导出格式，明文，用户指定位置 | 迁移到别的实现，或者人读 |
| 加密快照 | 数据目录打包，密文，加上用主密钥加密的校验信息 | 换机器 |

Time Machine 与 SQLite 的 WAL 模式有一个已知问题：备份可能拍到不一致的中间态。处理是定期做 checkpoint，把 WAL 合进主文件，并在快照前强制一次。

导出是明文，导出时界面要说：这个文件夹里是你的全部数据，没有加密，放好。

## 空间

估算给用户看，也给我们自己设计约束：

| 数据 | 量级 |
|---|---|
| 十万封邮件的原始记录，不含附件 | 5 到 10 GB |
| 附件 | 取决于人，常见 5 到 50 GB |
| Telegram 文本，五年 | 1 GB 以内 |
| Telegram 媒体，按 05 号的延迟下载策略 | 常见 2 到 20 GB |
| 向量与全文索引 | 原文的 3 到 4 倍 |
| 模型 | 5 到 6 GB |

所以一个普通用户第一年可能用掉 20 到 100 GB。09 号的首次运行要检查磁盘并诚实地说数字。回填过程中磁盘剩余低于阈值时暂停并提示，不把磁盘写满。这台 Mac mini 现在的状态就是我们要避免用户遇到的。

## 完整性

每次启动做一次轻量自检：库能打开、schema 版本匹配、账本哈希链完整、raw 与 blobs 目录里抽样几个文件能解密且哈希匹配。自检失败进入只读模式并提示，不带着坏数据继续写。

## 明确不做

- **不做多设备同步。** 单设备。
- **不做云备份。** 用户要备到云，用 Time Machine 加自己的方案。
- **不做自研数据库引擎。**
- **不做外部锚定。** 哈希链只为自查。
- **不做按条目的访问控制。** 单用户，进程内一律可读。02 号的级别是出境控制，不是存储控制。
