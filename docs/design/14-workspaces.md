# Genatrix · 工作空间

> 状态：草稿 v0.2 · 2026-11-03 · 按建议实施，待复核
> v0.2 变更：界面上"空间"取代工作页，每个空间一个首页。
> 回答的问题：一个人同时有几摊事，比如公司的工作和自己的项目，各自有自己的账号、仓库、执行器。怎样把它们像积木一样拼起来，而且互不影响，同时不把"一个人完整的数字生活"拆成几份？

## 为什么要这份文档

13 号的 Project 是一个仓库加一组规则，05 号的账号是一个个来源。两者之间没有任何关系：公司的飞书任务、公司的仓库、你个人项目的仓库、你的私人邮箱，都摆在同一个平面上。

这有两个问题：

1. **拼不起来。** 公司的飞书任务该交给哪些仓库、用谁的 Claude 订阅、以谁的 GitHub 身份推送，现在说不出来。
2. **隔不开。** 只要有一条路把 Item 交给执行器（05 号飞书一节的 L2 就是这样一条路），公司的内容就可能进个人项目的执行器，你的私人邮件也可能进公司仓库的执行器。现在靠的只是你每次自己留意。

工作空间就是把这两件事说清楚的那个单位。

## 底座不拆

先说不做什么：**工作空间不是几个 Genatrix，也不是几份数据库。**

00 号的出发点是一个人完整的数字生活。你只有一个；同一个同事会在飞书派活，也会给你的私人邮箱写信；每天的摘要要看到全部。人、Item、时间线、记忆、出境记录、审批仍然只有一份。

工作空间是在同一份底座上划出的范围，管两件事：**拼装**和**隔离**。

## 概念

```
Workspace  一个工作空间。名字、标题；它的账号；它的项目。
           它的执行器登录和代码托管身份，按名字存在各自的地方。
```

和已有概念的关系：

- **账号**（05 号）最多属于一个工作空间。不属于任何空间的账号就是你的生活，比如私人邮箱、Telegram。
- **项目**（13 号）恰好属于一个工作空间。没写的属于内置的 `personal` 空间。
- **Item** 不打标签。它来自哪个账号，就属于哪个空间。账号换了空间，它的 Item 跟着走，不用迁移数据。
- **执行器、角色、模板**是共用的定义，不属于某个空间。项目说明哪些执行器能看它的代码（13 号不变）；空间决定这些执行器以谁的身份登录。

内置一个 `personal` 空间，标题是"个人"。它没有账号，你的个人项目放在这里。它和别的空间一样可以改：加账号、改标题。

一个例子：

```
personal（个人）   账号：无               项目：genatrix
dpt（公司）        账号：飞书 ou_…、        项目：app、web、infra
                        公司邮箱
```

## 拼装

一个空间由这些积木拼成：

| 积木 | 在哪定义 | 空间里写什么 |
|---|---|---|
| 账号 | 05 号，设置页或终端登录 | 账号的名字，比如 `lark:ou_…`、`mail:neo@dpt.xyz` |
| 项目 | 13 号，项目文件 | 项目文件里写它属于哪个空间 |
| 执行器登录 | 13 号，`genatrix exec login` | 登录时说给哪个空间 |
| 代码托管身份 | 13 号，`genatrix github login` | 登录时说给哪个空间 |
| 测试 agent 等以后的执行器 | 13 号 | 同执行器 |

- **空间是一个定义文件**，和项目、模板一样按内容哈希版本化，由你提交。
- **执行器登录和代码托管身份按空间存。** 空间有自己的，就只用自己的；没有，就用默认的那一份。默认的那一份不属于任何空间，所以一个空间永远不会用到另一个空间的登录。公司给你开了 Claude 订阅或单独的 GitHub 账号，就给公司空间单独登录；没有，就和个人项目共用默认的。
- **连接器不变。** 一个账号仍然是一个连接器进程管的一个账号，空间只是给它加了一个归属。

## 隔离

隔离靠一条规则：

> **交给某个空间里执行器的 Item 内容，只能来自这个空间的账号。**

- 你当场写的话不受此限：那是你自己的决定，照常按 02 号过闸门。
- 这次派单自己的产出物也不受此限：它本来就属于这次派单。
- 不属于任何空间的账号，比如你的私人邮箱，它的内容不交给任何执行器。你要交，就把那段话写进任务，或者把这个账号放进某个空间。
- 这条规则和 02 号的级别是叠加关系，不是替代：属于这个空间的私人内容，仍然按 Personal 处理。空间解决的是"能不能给这些执行器"，级别解决的是"以什么样子给"。

执行在两处：

1. **起草派单时。** 派单从一个 Item 发起（比如一条飞书任务），它的来源账号必须属于项目所在的空间，否则拒绝起草，卡片上不会出现。
2. **派单开始运行时再查一次。** 起草到批准之间，账号可能换了空间、项目也可能换了空间。查不过就不运行，记录写明原因。

## 界面

- **底座的视图保持完整。** 时间线、摘要、搜索、人默认看全部。以后可以按空间筛选，第一版不做。
- **"空间"是做事的地方**（06 号 v0.14）：空间列表，每个空间一个首页，有待办、进行中、新工作、记录、组成五块。原来的工作页并进去。
- **对话里的"工作"段**（06 号 v0.12）保留，是跨空间的任务列表，任务行标出所在空间。
- **从任务派单**：任务的对话页有"派单"，落到这个空间首页的新工作，任务的标题、描述和链接填进任务一栏，项目只列这个空间的。任务不属于任何空间时，说明要先把账号放进一个空间。
- **设置页的账号**标出它属于哪个空间。

## 谁能改

添加、修改、停用一个空间，属于 02 号第 12 条的高权限操作，和添加项目一样：只接受本机请求或带管理口令的管理设备。把一个账号放进一个空间，就是决定它的内容可以交给哪些执行器。

## 不变量（提议，通过后并入 02 号）

30. 一个账号最多属于一个工作空间；一个项目恰好属于一个工作空间。
31. 交给执行器的 Item 内容只来自这次派单所在空间的账号。这一条在起草和开始运行时各查一次；不属于任何空间的账号的内容不交给任何执行器。
32. 派单用它所在空间的执行器登录和代码托管身份；空间没有自己的，用不属于任何空间的默认那一份，绝不用另一个空间的。
33. 添加、修改、停用工作空间是第 12 条的高权限操作。

## 明确不做

- **不拆底座。** 不按空间分数据库、分密钥、分出境记录。将来真需要物理隔离，比如公司要求公司数据单独加密，另立文档。
- **不做团队空间。** 一个人，自己的几摊事。13 号"不做团队协作"不变。
- **第一版不做按空间筛选时间线、摘要和搜索。**
- **不按空间分执行器、角色、模板的定义。** 它们是工具，不是数据。
- **不自动把账号放进空间。** 归属是你决定的事。

## 与其他文档的接口

- 01 号：不变。Item 不加字段，归属由来源账号推出。
- 02 号：不变量 30 到 33；第 12 条的高权限操作多一项。
- 05 号：飞书一节的 L2"项目对应任务清单"在空间之下：空间先有飞书账号，项目再说明它从哪些清单接活。
- 06 号：工作页按空间分组；任务行标出空间；从任务派单；设置页的账号标出空间。
- 13 号：Project 多一个 `workspace` 字段；执行器登录和 GitHub 身份按空间；派单的来源 Item 与第 31 条。

## 待裁决

1. 工作空间是在同一份底座上的范围，不拆数据。我主张如此：拆了就失去了"一个人"这个前提。
2. 账号最多属于一个空间，不属于任何空间的账号的内容不交给任何执行器。我主张如此：默认不给，比默认给安全；要给，就把账号放进空间，这是一次明确的决定。
3. 执行器登录和代码托管身份按空间存，没有就用默认的。我主张如此：大多数人只有一份，强制每个空间单独登录是负担；但一个空间永远不用另一个空间的。
4. 公司内容的开关（05 号飞书一节 L2 原来说的"按项目开关"）改成按空间：一个空间可以声明"本空间的内容以原样交给本空间的执行器"。我主张如此，放到 L2 一起做；在那之前，空间里的私人内容仍按 Personal 脱敏，你可以在卡片上把它调成公开。
