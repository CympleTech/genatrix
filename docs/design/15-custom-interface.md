> 回答的问题：界面要能由你、或者你让 AI 随意修改，而且改了不用重新编译、重新打包 core。前后端怎样分开，才不会让界面的修改处处受限，同时不让一段改过的界面代码绕开 02 号的信任边界？

## 为什么要这份文档

现在的界面（06 号）是编进 core 的：`web/` 构建出来的文件在编译时打进二进制，改一个按钮的颜色也要重新编译、重新发布。接口也是照着这一个页面裁的，很多是"一个页面一个接口"，页面想换一种组合方式就得改后端。

你希望界面是你的：按自己的习惯排布，想加一个视图就加，而且这件事可以交给 AI 做。只要界面和 core 绑在一起，这就做不到。

但界面不是普通的皮肤。它运行在已配对设备的浏览器里，拿着这台设备的身份，能读到这台设备能看到的一切；审批按钮也在它里面。11 号已经因为这一点裁决过"不运行 agent 提供的界面代码"。所以这份文档要同时回答两件事：怎样分开，以及分开以后谁守边界。

## 两类需求

界面上的需求分两类，处理方式不同：

1. **呈现。** 布局、一页放哪些东西、排序、筛选、组合、配色、多一个视图。数据和动作 core 都已经有了。这一类**永远不该碰 core**。现在会碰，是因为接口太专用。
2. **新能力。** 新的数据来源（新连接器）、新的对外动作、新的计算（比如"每个执行器的审查通过率"）。这一类以后也要碰后端，但碰后端不等于重编 core：新的计算交给 11 号的 agent，装上即生效；只有改信任边界的事（新连接器、新的动作种类）才需要新版 core。这本来就该如此，因为它们决定什么能离开这台机器。

目标不是让界面无所不能，而是让第一类需求只改界面，第二类大多走 agent。

## 四层

```
可信外壳     core 自带，固定。审批、口令、凭据、配对、高权限操作、安全模式、界面切换、外部链接
界面         数据目录里的一组静态文件，由你批准的版本。你和 AI 改的是这一层
数据接口     有版本、只加不减、按资源组织；随 core 发布接口描述
agent 视图   agent 产出的结构化数据，经数据接口给界面
```

### 可信外壳

外壳是 core 自带、不可定制的那一小部分，是信任决定发生的地方：

- **审批。** 动作卡片的显示、批准、拒绝、修改后批准。卡片仍按 03 号和 11 号的固定结构由外壳渲染。
- **口令和凭据。** 管理口令、邮箱密码、Telegram 和飞书登录、GitHub 令牌、执行器登录。
- **配对和设备。** 配对码、撤销设备、授予管理角色。
- **高权限操作。** 02 号第 12 条的那些，以及空间、项目、模板、角色的登记。
- **安全模式。** 一个固定地址，总是打开 core 内置的默认界面，用来从一个坏掉的界面里退出来。
- **界面的选择和批准。** 这台设备用哪个界面，新版本的预览和批准。
- **外部链接。** 见下面"数据出不去"。

外壳是顶层页面，界面嵌在它里面运行。外壳之外，界面想画什么都可以；外壳之内，界面碰不到。

### 界面

一个**界面**是一组静态文件（页面、脚本、样式、图标），加上一份说明：名字、依赖的数据接口版本、文件清单和各自的哈希。

- **放在数据目录里**，不编进 core。core 自带一份默认界面，就是现在的 `web/`，作为起点和兜底。
- **按内容哈希登记版本**，和 13 号的项目、模板一样。每一版都留着，可以回到任何一版。
- **新版本由你批准才生效。** 批准前可以在这台设备上预览。批准卡片写明：改了哪些文件、大小、依赖的接口版本，以及哪几台设备在用这个界面、会跟着变。
- **源码和构建结果一起保存**，下次改的时候 AI 从源码改，而不是从压缩后的产物改。默认界面的源码随 core 一起发布。

### 每台设备选一个界面

界面有名字，比如"电脑"、"手机"、"默认"。**每台设备选一个界面用**（2026-11-14 裁决：按设备，可以跟随别的设备或复制），几台设备可以用同一个：

- **新设备第一次打开**时，外壳问一次：用默认界面，跟另一台设备用同一个（列出每台设备和它在用的界面），还是复制一个再改。
- **跟随**：两台设备用同一个界面，改它，两台都变。
- **复制**：从某个界面复制出一个新界面，归这台设备，之后各改各的。
- **随时可以切换**：外壳里有"界面"入口，列出所有界面、谁在用、最近一版是什么时候批准的，点一下这台设备就换过去。切换只是选择一个已经批准过的版本，不需要再批准。
- 这台运行 Genatrix 的电脑本身也是一台设备，同样选一个界面。

### 数据出不去

界面的代码你基本没法逐行审，AI 写的更是如此，所以安全不能靠审代码，要靠结构：

- **界面不直接拿设备身份。** 它运行在外壳里一个隔离的框架中，没有这台设备的登录凭据，也读不到外壳。它访问 core 的每一个请求都经外壳中转，外壳按清单分四种处理：
  - **直接放行**：读数据、起草动作、提问、给 agent 发话、回答执行器的问题这类，结果本来就要你再批准，或者只是读。
  - **外壳确认**：高权限操作（02 号第 12 条、空间和项目的登记、填和移除令牌、接入和移除账号、安装和卸载 agent），以及删除对话、标为垃圾、彻底删除、停止派单、调低级别这类不可撤销或放宽边界的操作。界面可以发起，外壳弹出它自己渲染的确认，写明是什么请求、对象是谁、带了哪些字段（密码和令牌只写"已填"），你在外壳里点了才发出；core 要口令时，口令也在外壳里输入。
  - **交给外壳审批**：批准、拒绝、修改后批准一个动作。界面里的卡片只显示，点"审批"就请外壳打开；外壳按编号向 core 重新取这张卡片，按固定结构渲染，你在那里决定。界面没法把一张卡片画成别的样子骗你批准。
  - **只在外壳里**：配对、撤销设备、授予管理角色、管理口令、导出和删除全部、界面的选择和批准。界面里只有一个"打开设备与安全"的入口，点了由外壳打开它自己的面板。
  - 清单之外的请求按"外壳确认"处理，宁可多问一次。
- **凭据可以在界面里填。** 邮箱密码、令牌在界面的表单里填，交给 core 的请求先经外壳确认。界面只能和 core 说话，所以它拿到凭据也送不出去。
- **界面只能连 core。** 浏览器层面不许它加载外部的脚本、图片、字体，不许它连任何别的地址，也不许它把自己导航到别处、打开新窗口。没有这几条，一张外部图片的地址就能把数据带出去。
- **地址栏归外壳。** 界面里切换页面，告诉外壳，由外壳记进地址栏；刷新、返回、分享链接都照常，链接打开时外壳把路径交给界面。
- **界面的文件谁都能取。** 和现在的页面一样，未配对的访问者也能取到界面的文件：它们按哈希寻址，只是代码，不含你的数据。数据只经外壳、凭这台设备的身份拿。
- **外部链接经外壳打开。** 界面要打开一个外部地址（比如 GitHub 上的 PR），交给外壳；外壳显示完整的目标地址，你点了才打开。地址里夹带的东西在这里看得见。
- **起草的动作仍然要批准。** 界面能起草一封邮件、一张派单卡片，但它们只会出现在外壳的审批里，按固定结构显示。界面没法把一个动作画成别的样子骗你批准。

这样，一个坏界面最多是难用、显示错，它拿不走数据，也替你做不了决定。

### 数据接口

现在的接口是给默认界面裁的。要让界面的修改不碰 core，接口要变成一份稳定的契约：

- **按资源组织的读接口。** Item、对话、人、任务、派单、项目、动作、记录，带筛选、排序、分页。界面自己组合，不再要求"一个页面一个接口"。现有的专用接口保留，默认界面继续用。
- **有版本，只加不减。** 字段和接口可以加，不改含义、不删。真要改，就出一个新版本，旧版本保留到没有界面用为止。
- **core 告诉界面自己是谁。** 一个固定的接口说明 core 的版本、接口版本、有哪些能力（比如有没有装某个 agent）。界面说明自己依赖哪个接口版本；core 不满足时，外壳说明原因并回到默认界面。
- **接口描述随 core 发布。** 机器能读的接口描述，和由它生成的类型。AI 改界面时照着它写，不需要读 core 的代码。
- **权限不变。** 界面经外壳能读到的，就是这台设备本来能看到的，不多一分。
- **第 1 版（v0.3）**：`/api/meta` 说 core 的版本、讲哪些接口版本、有什么能力（模型是否就绪、能否按意思搜索、有没有 GitHub、哪些 agent 发布了视图）。`/api/v1/` 下是只读的资源：消息（按时间、对话、人、来源、方向、级别、文字筛选，一页一页取）、单条消息、对话、人、任务、承诺、派单、动作、项目、空间、记录、agent 视图。列表都回 `{rows, next}`。契约是一份 JSON，写明每个接口、参数、字段，以及外壳和界面之间的消息；它和 core 一起发布，在 `/api/v1/schema` 能取到，每个界面的源码仓库里也放一份 `API.json`。有测试保证契约里写的接口都有、有的接口契约里都写了。写操作仍走原来的接口，由外壳按清单处理。

### agent 视图

"每个执行器的审查通过率"这种需求，数据都在，缺的是一段计算。不该为它重编 core，也不该让界面自己去拉全部派单记录来算。

11 号的 agent 现在能读数据、能提动作。再给它一种输出：**视图**，一份带固定结构的数据（表、序列、若干数字和文字），经数据接口按名字取。界面拿到的只是数据，怎么画是界面的事。agent 仍然不能提供界面代码（11 号第 4 条裁决不变）：数据由 agent 算，代码由你批准的界面出，两者不混。

落地（v0.3）：清单里 `[[views]]` 声明名字和标题；运行中调用 `views.publish` 发布，核心检查结构和大小后按"agent + 名字"只留最新一份，记下运行的级别；卸载 agent 时一起删。内置界面在 agent 的对话详情里画出它的视图。细节见 11 号 v0.2。

## 悬浮对话框（v0.4）

调界面最顺手的方式是看着页面直接说。所以外壳右下角有一个悬浮按钮，点开是一个对话框，在任何页面、任何界面下都在，界面坏了也在：它是外壳的，不是界面的。

- **两种说法。** 上面一个切换：
  - **问**：问你的数据、问这一页怎么用，由本机的模型回答，和"问"一样；对话框把你在哪一页一起告诉它。
  - **改这一页**：说你想怎么改，就起草一张改界面的派单（下面一节），写明你当时在哪一页、用的是哪个界面；外壳当场打开卡片让你审批。
- **进度在对话里，效果在页面上（v0.5）。** 批准后页面转到这次派单的进度；执行器在做什么、有没有问你问题，都出现在对话里，问题可以直接在对话里回答，和派单页一样经闸门交回同一个执行器。做完时页面回到你提要求的那一页，直接以预览显示改好的样子（只在这台设备上），对话里给“启用”和“不要”；启用就是批准这个版本。没做成时对话写明原因，给“让它修好”：同样的要求加上失败的原因，再起草一次。
- **问错了地方时。** 在"问"里说了一句像是要改页面的话（"默认只显示最近几条"、"把按钮挪到上面"），对话框不交给模型，先问一句"这是想改这一页吗？"，给"改这一页"和"只是问问"两个按钮：回答问题的模型改不了页面，交给它只会得到一句编出来的话。交给模型的问题里也写明它改不了界面，遇到这种要求就直说，并指向"改这一页"。
- **用的是内置界面时**，没有源码可改，对话框说明这一点，并给一个按钮：复制内置界面、在这台设备上用它，然后接着改。
- **一次接着一次。** 改界面的派单做完时，界面的源码仓库前进到这次的提交，下一次就在它上面接着改；你批准了更早的一版（用回这一版）时，源码也回到那一版。
- **对话不是记忆**（03 号）：只在打开着的页面里，关掉就没了；不进记忆，不存进浏览器。
- 它能做的就是外壳本来能做的：问走"问"的接口；改走起草和审批；批准仍是你在外壳里点。

## 让 AI 改界面

这正好是 13 号已有的流程：

- 每个界面的源码是一个项目，属于一个专门的"Genatrix"空间。
- 你说"把派单页改成按项目分组"，就起草一张派单卡片，照常批准。执行器在工作区里改源码、构建，交回提交。
- 构建结果成为这个界面的一个待批准新版本。你在这台设备上预览，满意了批准；不满意就继续说，或者丢掉。
- **执行器只拿到界面的源码和接口描述**，拿不到你的任何数据：改界面不需要看你的邮件。预览是在你的设备上，用你的数据，执行器看不到。

你也可以自己改源码，交上去是同样的批准流程。

落地（v0.3）：

- **源码仓库。** 复制内置界面时，core 用随它发布的源码（不含外壳的文件）在数据目录里建一个 git 仓库，放进 `API.json`（接口契约）和 `GENATRIX.md`（界面在沙箱里怎么运行、怎么构建、哪些文件别动）；复制一个有源码的界面，就复制它的仓库。从文件夹登记的界面没有源码，面板上写明，没法让 AI 改。
- **项目。** 这个仓库登记成 `ui-<界面>` 项目，在内置的"Genatrix"空间里（14 号）：这个空间没有账号，所以任何账号的内容都交不到它的执行器（第 31、38 条）。允许的命令是 `npm run build` 和 `npm run check`，不联网。
- **依赖只读（v0.6）。** 共用的包谁都不能写，构建和检查也一样：构建的设置保证它不往里写临时文件。源码里归 Genatrix 管的文件（`GENATRIX.md`、`API.json`、`vite.config.ts`、`.npmrc`、`.gitignore`，以及 `package.json` 里的构建和检查两条脚本），每次让 AI 改之前更新成这一版 core 的；界面自己的其他东西不动。
- **依赖。** 构建要的包由你在这台电脑上运行一次 `genatrix ui deps` 备好（用 npm 按锁定的版本装，或者从一个已有的 node_modules 复制），放在执行器的组能读、不能写的地方；每个界面仓库里一个链接指向它。执行器不装包，也不联网。
- **构建由宿主做（v0.5）。** 执行器改完、提交之前，宿主在它的工作区里、以执行器的用户、用它的搜索路径、不联网，运行一次 `npm run build`。执行器有没有自己构建、被不被允许构建，都不影响有一份构建可看。构建失败，派单就以失败结束，记录里是构建最后说的几行。
- **派单。** 界面面板里"让 AI 改"，写一句想怎么改，就起草一张内置流程 `change-interface` 的派单卡片，外壳当场打开让你审批。执行器改源码、构建、提交。
- **回来。** 做完时 core 从最后一个提交里取 `dist/`，按界面文件的规矩检查后登记成这个界面的待批准版本，派单记录写明"在界面里等你批准"。不提议推送、不开 PR。之后照常预览、批准。

## 不变量（提议，通过后并入 02 号）

34. 界面运行在可信外壳之内的隔离框架中，不持有设备的登录凭据；它对 core 的每一个请求都经外壳按清单处理。批准和拒绝动作只在外壳里，按外壳向 core 重新取得的卡片做；配对、设备、管理口令、导出和删除全部只在外壳的面板里；高权限请求由外壳显示内容、你在外壳里确认后才发出，口令只在外壳里输入。
35. 界面只能和 core 通信：不加载外部资源、不连接其他地址、不自行导航或打开窗口。外部链接经外壳显示完整地址，由你打开。
36. 删除和停止这类不可撤销的操作，由外壳渲染确认、由你在外壳里确认后才执行。
37. 一个界面版本只有经你批准、按内容哈希固定后才在设备上运行；core 内置的默认界面和安全模式始终可用。
38. 修改界面的执行器只拿到界面的源码和接口描述，不拿到 Item 或任何个人数据。

## 明确不做

- **不让 agent 提供界面代码。** 11 号的裁决不变：agent 只提供视图数据。
- **不让界面绕过外壳。** 没有"信任这个界面"的开关。
- **不做界面市场。** 第一版的界面来自默认界面、你自己、你的执行器。从别人那里装一个界面，就是在你的设备上运行别人的代码，等外壳的约束跑稳了再谈。
- **不允许界面联网。** 天气、地图、字体这类外部资源一律没有；要用就打包进界面。
- **不为了界面放宽接口权限。** 接口能给的，仍然只是这台设备能看到的。

## 已裁决（2026-11-14，按建议通过）

下面四条按建议通过。


1. **构建在哪里做。** 我主张在执行器的工作区里构建，构建结果随提交交回，core 只检查文件清单、大小、依赖的接口版本，不在 core 里跑构建工具。代价是构建需要的依赖要能离线获得：默认界面的依赖锁定版本，随源码一起备好，执行器构建时不联网。
2. **界面批准的权限。** 我主张：只影响这台设备的界面，这台设备自己能批准；一个界面有别的设备在用，批准新版本是高权限操作（本机，或带口令的管理设备），因为它改变别的设备上运行的代码。
3. **默认界面跟着 core 升级。** 我主张：默认界面随 core 更新；你复制出来的界面不自动变，core 升级后如果有新的接口版本，外壳提示"默认界面有更新"，由你决定要不要让 AI 把改动合进你的界面。
4. **外壳的范围**按上面列的那些。以后若有一块需要从界面挪进外壳，或者反过来，改这份文档。
